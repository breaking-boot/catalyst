# CLAUDE.md — Agent guidance for catalyst

## What this project is
Browser extension (Manifest V3, Chromium-based browsers — Chrome and Brave; Firefox support is planned) that augments Boot.dev. The browser-loadable directory is `bootdev-extension/`. Everything else (`reference_data/`, `scripts/`, docs) is development support only and is never loaded by the browser.

## File responsibilities

| File | Owns |
|------|------|
| `src/injected.js` | Runs in the page's JS context. Wraps `fetch` and `XMLHttpRequest` to clone `api.boot.dev` JSON responses and relay them to the content script via `window.postMessage`. Also owns the bearer-token replay bridge (`BE_FETCH_JSON`) and `AUTH_REQUIRED_PATHS`/`AUTH_REQUIRED_PATTERNS` — the paths whose requests must be **queued** until an `Authorization` header has been harvested, rather than sent bare and 401'd. No feature logic here. |
| `src/content.js` | Isolated-world content script. `window.postMessage` listener and URL router only. Calls handlers defined in the feature files below. Also owns the `storage.onChanged` listener that live-applies settings (`applyFeatureSettings`) and reloads imported data on the `be_import_broadcast` signal (`applyImportedData`), plus the first-run settings prompt. Must be listed last in `manifest.json`. |
| `src/utils.js` | Shared helpers: `waitFor`, `chromeGet`/`chromeSet` (local) and `chromeGetSync`/`chromeSetSync` (sync), `toast`, `escapeHtml`, number formatters, shared constants (`TOP_NAV_BAND_PX`), and the rename tripwires `warnOnce`/`reportUsableFields`. No feature logic. Must be listed first in `manifest.json`. |
| `src/settings-schema.js` | Canonical, dependency-free settings schema: `SETTINGS_DEFAULTS`, `FEATURE_TOGGLES`, `PERSONAL_BOARD_TOGGLES`, `COMPARISON_BOARDS`. A toggle's `desc` is the full explanation shown on the options page; an optional `shortDesc` is what the popup shows instead (one sentence, no caveats) — add it only when the full text is too long to skim. Single source of truth shared by the content script (`settings.js`) and the extension pages (`popup.js`) so defaults/labels can't drift between contexts. Data only. Loaded right after `utils.js` (content script) and via `<script>` before `popup.js` (extension pages). |
| `src/settings.js` | Feature on/off model. `be_settings` in `chrome.storage.sync`, default-on (except `versionCheck`, `bossTracker`, `submitConfirm`, and `assignmentShortcuts`, default-off). `loadSettings`, `isFeatureEnabled(key)`, `isComparisonEnabled(boardKey)` / `isPersonalBoardEnabled(boardKey)` (the relevant master AND the per-board flag), `setFeatureEnabled(key, value)` (single-flag write from the content script; patches only that key into the raw stored object). Consumes `SETTINGS_DEFAULTS` from `settings-schema.js`. No feature logic. Loaded after `settings-schema.js`. |
| `src/updateCheck.js` | Opt-in GitHub release check (`versionCheck`, default-off). Throttled to once/24h; toasts when a newer release exists, or (when off) a one-time toast nudging the opt-in. Uses the CORS-open GitHub API, so no host permission is needed. |
| `popup.html` / `options.html` / `popup.js` / `popup.css` | Settings UI (extension pages, not injected). `popup.html` is the toolbar popup (`action.default_popup`); `options.html` is the options page (`options_ui`) and adds the per-board Personal Leaderboards toggles, the per-board comparison toggles, the `versionCheck` opt-in, and the Backup & restore section. Both share `popup.js`/`popup.css` and load `src/settings-schema.js` first for the shared defaults/labels (`options.html` also loads `src/backup.js`). They write `be_settings` to `storage.sync`; `content.js` live-applies via `storage.onChanged`. |
| `src/backup.js` | Backup & restore core: owns the backup file format (`BACKUP_FORMAT_VERSION`, versioned independently of the extension), builds the export from storage, validates/upgrades uploaded files, and merges them back — data merges (handles union, snapshot series merge, boss highs max with a same-`eventId` check for the event high), settings replace wholesale. Dependency-free like `settings-schema.js`; loaded only by `options.html` via `<script>` before `popup.js`, **not** a content script. A successful import ends by writing `be_import_broadcast` (storage.local) so open tabs reload the imported keys. Mirrors a few helpers/constants from `utils.js`/`leaderboard.js`/`boss.js`, each marked "keep in sync". |
| `src/leaderboard.js` | All-time leaderboard injection and personal leaderboards feature. |
| `src/profile.js` | Cumulative XP display on public profile pages. |
| `src/boss.js` | Boss-event tracker: state management, render, drag-to-reposition, background refresh, settings panel, near-high notification, and event-active detection via `Event.ExpiresAt` (polling stops between events). Also owns the boss-event reminder toast (`bossReminders`) shown when the tracker is hidden and an event is live. |
| `src/nextLesson.js` | Next Lesson top-nav link and Alt+N keyboard shortcut. |
| `src/submitConfirm.js` | Optional confirmation before a code-lesson submission (`submitConfirm`, default-off). One capture-phase `click` listener on `document` cancels **pointer** activation of Boot.dev's native Submit button and opens a `<dialog>`; confirming re-invokes that same native button. The guard fires only on `event.isTrusted && event.detail > 0`, which scopes it to pointer clicks, leaves `Ctrl+Shift+Enter` alone, and makes the confirm-path `.click()` (untrusted) impossible to re-intercept — no bypass flag, no recursion. Nothing is injected into Boot.dev's controls, so rerenders and SPA navigation need no recovery logic. |
| `src/cliShortcuts.js` | CLI command copy shortcuts: `Alt+C` copies `bootdev run <uuid>`, `Alt+Shift+C` copies it with `-s`. Route UUID and displayed commands are read **at keypress time** — nothing cached, observed, or stored. Capability comes from what the page renders (a safe submit-only lesson has no run command, and one is never derived by editing the submit command). Clipboard via `navigator.clipboard.writeText` under the keypress gesture; no permission needed. |
| `src/assignmentShortcuts.js` | Checklist keyboard shortcuts (`assignmentShortcuts`, default-off): `Alt+1`–`Alt+9` toggle the matching top-level step, `Alt+0` checks the next unfinished box, `Alt+`` returns focus to the answer side. Works on `/lessons/<uuid>` **and** `/challenges/<uuid>` (`lessonOrChallengeUuidFromPath`). Everything is read at keypress time — no cache, no observers, no storage. The checklist is scoped to `#markdown-side` and the answer side is everything in `#lesson-container` outside it; hierarchy is modelled by one rule (a step is top-level when its **nearest** `<li>` has no `<li>` ancestor). Capture-phase listener that stops propagation only once a target resolves, which is what lets it beat the course terminal to the keystroke. |
| `src/trainingGrounds.js` | Training Grounds difficulty **level** filter: a "Difficulty Level" section injected into the challenge-search filter popover offering the exact levels inside whichever tier Boot.dev's own difficulty filter has selected (Hard → 8/9/10). Also owns the per-row level badges. Mirrors the native pills — picks are pending until Boot.dev's Search commits them; the committed state is per-tab, carried in the page URL (`dl=`), handed to `injected.js` via the `data-be-dl` attribute, and never stored. The response filtering itself lives in `injected.js`. |
| `src/styles.css` | All injected UI styles. Uses `be-` prefix on all class names to avoid clashing with Boot.dev's own styles. |
| `assets/` | Bundled static art (loaded by the browser, unlike `reference_data/`). `frames/0.png`–`9.png` are avatar role frames indexed to `ROLE_FRAME_INDEX_BY_ROLE` in `leaderboard.js`, loaded into the page via `chrome.runtime.getURL` + `web_accessible_resources` (`use_dynamic_url`) as the fallback when the API gives no frame URL. `maptexture2.webp` is the boss-panel + settings-page background, referenced by `styles.css` (via `../assets/`) and `popup.css` — both extension-owned stylesheets, so no `web_accessible_resources` needed. Both are copies of Boot.dev art, bundled with Boot.dev's permission — see `ATTRIBUTION.md`. |
| `manifest.json` | MV3 manifest. Do not add permissions without explaining why. Current permissions: `storage` only (covers both `storage.local` and `storage.sync`). Declares `action.default_popup` (popup.html) and `options_ui` (options.html). |

## Architecture rule (DOM scraping is a last resort)
Boot.dev is a Nuxt/Vue SPA. Its CSS class names are hashed and rebuilt on every redeploy. **Avoid reading data by scraping the DOM unless absolutely necessary.** As much data as possible must come from intercepted API responses; the DOM is primarily for locating injection anchors and writing UI. When a value has no API source at all (e.g., the platform-wide student count, which Boot.dev only server-renders into the page payload), reading it from rendered text is acceptable as a last resort — match on stable text landmarks, never hashed classes, and read only the minimum needed. See `src/leaderboard.js` `findTotalStudents` for the canonical example, and `findNuxtCurrentUserHandle` (same file) for the other sanctioned case: the signed-in user's own handle, which has no API source because every user endpoint requires already knowing the handle. That one parses `#__NUXT_DATA__` (devalue: a flat array where each field value is an *index* into it) at most once per page load, because the payload runs to hundreds of KB and the DOM scan ticks every 2 seconds.

Interception flow:
```
page fetch/XHR → injected.js (page context) → window.postMessage → content.js router → feature handlers
```

## Injection anchor priority
When finding where to inject UI elements, prefer stable hooks in this order:
1. Element `id`
2. `data-*` attributes
3. `aria-*` attributes
4. Semantic HTML tags
5. Visible text content landmarks
6. CSS class names — if used, add a `// FRAGILE: hashed class, may break on redeploy` comment

## Content script load order
Files share a single global scope — no ES module syntax (`import`/`export`), no build step, no bundler. `manifest.json` loads them in order:

```
utils.js → settings-schema.js → settings.js → leaderboard.js → profile.js → boss.js → nextLesson.js → updateCheck.js → trainingGrounds.js → submitConfirm.js → cliShortcuts.js → assignmentShortcuts.js → content.js
```

`utils.js` first so helpers are available everywhere; `settings-schema.js` next so the shared defaults/labels exist; `settings.js` after that so `isFeatureEnabled`/`isComparisonEnabled` are available to every feature. `content.js` last so the router can call handlers already defined by the feature files.

(`popup.js` runs in the extension-page context, not the content-script scope, so it can't see the feature files — but it loads `src/settings-schema.js` via its own `<script>` tag, so the popup and the content script share exactly one copy of the defaults, labels, and board ordering. Keep the settings key string (`be_settings`) aligned between `popup.js` and `settings.js`.)

## Conventions
- `FIXME` comments mark field names inferred from context that should be verified against real API responses in `reference_data/`.
- `chrome.storage.local` keys for boss data: `be_boss_state` (tracker stats, including `eventHighAt` — when the event high was last raised), `be_boss_ui_state` (panel position/minimized), `be_boss_reminder_state` (reminder bookkeeping, per-device), `be_boss_inactive_notice` (last "no active event" toast timestamp). The Training Grounds level selection is deliberately **never written to storage** — it is per-tab and carried in the page URL (`dl=8,10`, alongside Boot.dev's own `d=hard`), matching how the native filters derive from the URL. Its one piece of memory is `rememberedChallengeSelection`, a module-level variable in `trainingGrounds.js` that lives only as long as the tab; see the SPA-navigation bullet below for why it exists and why it cannot resurrect a dropped filter. Feature settings live in `chrome.storage.sync` under `be_settings`. `be_import_broadcast` (storage.local) is the import signal: written by `backup.js` after a successful options-page import, consumed by `content.js` to reload imported keys in open tabs — tabs deliberately do NOT react to the data keys themselves, because they write those keys routinely and would loop on their own writes.
- Gate any new feature behind a flag in `settings-schema.js` (`SETTINGS_DEFAULTS`, default-on; the four exceptions are `versionCheck`, default-off because it can reach off-device, `bossTracker`, default-off because the panel must be quiet until the user opts in, `submitConfirm`, default-off because it interposes a step in front of a native Boot.dev action, and `assignmentShortcuts`, default-off because it claims ten Alt+digit combinations even while the user is typing) and a toggle rendered from `FEATURE_TOGGLES`/`PERSONAL_BOARD_TOGGLES`/`COMPARISON_BOARDS`; check `isFeatureEnabled`/`isComparisonEnabled`/`isPersonalBoardEnabled` at its render/request entry and tear down cleanly when off. Because the schema is shared, adding a key in one place covers both the content script and the settings pages.
- All injected DOM elements use the `be-` CSS class prefix.
- Do not add `console.log` for debugging; use `console.debug` so it can be filtered.

## Off-limits / reference_data policy
- `reference_data/` — **never delete** any file here. Direct data captures (HTTP responses/requests, site HTML, `.har` files, and similar raw captures) must not be edited either — they are evidence and must stay faithful to what was captured.
- Non-capture reference docs in `reference_data/` — e.g. `bootdev_api_info/bootdev_openapi.yaml` (a work-in-progress spec), `bootdev_frontend_reference/bootdev_palette.css`, and `leaderboard_dom_notes.md` — **may be edited** to add clarifying comments or to refine them as we gain more data/clarity while building features. Improve them; just don't delete.
- `scripts/` — development, verification, and packaging utilities only; not part of the browser-loaded extension.

## API endpoints used (summary)

**The v0.12.2 audit read live and field-checked all 11 concrete endpoint variants Catalyst uses on 2026-07-31** (bundle: `reference_data/catalyst_versions/v0.12.2_api_casing_audit/`). The bullets below summarize them by route family, so one bullet may cover multiple concrete variants and `/v1/leaderboard_xp/day` is repeated to document its special personal-board role. Only `/v1/challenges/search` and `/v1/boss_events_progress` serve camelCase; the other nine are PascalCase. Boot.dev migrates casing **per DTO, not globally** — the same page payload carries a PascalCase user object next to camelCase achievement objects — so assume any single endpoint can flip on its own schedule and never assume a global switch.

**Auth:** `/v1/boss_events_progress`, `/v1/dashboard_content`, and **both `/v1/league_leaderboard_xp/*` boards** return 401 to a cookie-only request; they need the `Authorization` header `injected.js` harvests from Boot.dev's own traffic. All four are in `AUTH_REQUIRED_PATHS`/`AUTH_REQUIRED_PATTERNS` so a request made before a header is seen is queued, not sent bare. Every other endpoint works on the session cookie alone.

- `/v1/leaderboard_xp/{period}` and `/v1/league_leaderboard_xp/{period}` — leaderboard data; period = day | week | month | alltime. The `day` boards are **rolling last-24-hours** windows (user-reported), and their entries carry both `XPEarned` (trailing-24h XP) and `XP` (lifetime total). `XPEarned` for a given handle is identical on the global and league daily boards (verified 2026-07-31), which is what makes the league board a valid fallback. **`TotalXP` does not exist** on any leaderboard entry — nor do `IsCurrentUser`/`IsSelf`/`IsMe`. On the all-time board `XPEarned` ≈ `XP` but is not always exactly equal (24 of 25 matched on 2026-07-31)
- `/v1/users/public/{username}` — public profile; cumulative XP is at `data.XP`. **Carries no karma field in any casing** — karma comes from `/stats` only, so a tracked user's karma series advances on `/stats` refreshes and karma-board sightings, never on a profile fetch
- `/v1/users/public/{username}/stats` — public stats including karma
- `/v1/users/public/{username}/activity_heatmap?timezone={IANA}` — per-day activity counts (`data.Calendar`; includes 0-XP resubmits) plus a separate `data.GithubCommits` series (streak-only, no XP); feeds the personal daily-XP estimate tier
- `/v1/boss_events_progress` — boss tracker source of truth; new-event detection keys off `Event.UUID`
- `/v1/dashboard_content` — Next Lesson source via `CurrentLessonUUID`
- `/v1/leaderboard_xp/day` — exact personal-board daily XP when a handle appears there; every sighting also yields a backdated total-XP snapshot (`XP − XPEarned` at now−24h)
- `/v1/challenges/search` — Training Grounds challenge search (`q` required, `t`/`l`/`d` optional); one response carries the complete result array (bare JSON array, no count metadata; the page paginates it locally 10/page), and `topics.difficulty` (1–10) drives the Catalyst level filter. **`d=easy|medium|hard` is Boot.dev's own server-side tier filter, added 2026-08-01** — one value at a time, bounds confirmed exactly (easy 1–4, medium 5–7, hard 8–10, zero leakage across four captures). Catalyst reads `d` and never writes it. **Casing warning:** this response was PascalCase (`Topics.Difficulty`) on 2026-07-14 and camelCase (`topics.difficulty`) by 2026-07-30 — `challengeDifficulty` (injected.js) reads both

Confirmed API response field names are documented in `reference_data/bootdev_api_info/bootdev_openapi.yaml`

## Notes

- Boss chest tier names are inferred from the rendered modal order because `boss_events_progress` contains chest UUIDs and thresholds, not display names.
- Alerts are in-page toasts; the extension does not request the browser's `"notifications"` permission.
- Per-event boss stats reset automatically when `Event.UUID` changes. The all-time high persists across events.
- Boss polling stops between events: a response whose `Event.ExpiresAt` is in the past marks the event inactive, halts the 2-min poll, and shows a "no active event" toast at most once per 24h per device (timestamp in `be_boss_inactive_notice`, storage.local). A response with **no readable event identity** (`Event.UUID`/`Event.StartsAt` both absent after normalization) also counts as inactive: it must never trigger the reminder toast (the missing-expiry fail-open used to make it look "active") and never resets the stored per-event stats. A forced re-check (navigation, manual Refresh, tab focus) or Boot.dev's own passive `boss_events_progress` fetch resumes polling when a new event starts.
- **Boss casing — this endpoint is mid-migration and the normalizer is load-bearing today.** The live-event capture (2026-06-26) is PascalCase; between-events captures on **2026-07-16 and 2026-07-31** are entirely camelCase (`event.uuid`, `xpBonus`). `normalizeBossProgressJson` (boss.js) maps camelCase onto the PascalCase names the rest of the file reads. As of v0.12.2 it reads **per field** via `pickField(obj, Pascal, camel)` rather than gating on the shape of the whole response. The old gate bailed out whenever `Event` was present, so a **mixed** response (a live event restoring `Event` while leaving `xpBonus` camel) would have passed through without normalizing `XPBonus`; the `cur.bonusPct != null` guard would then have skipped the aura write while still allowing the updated timestamp to render. No mixed production response has been captured. `scripts/check_boss_normalizer.mjs` pins the two captured shapes plus a synthetic mixed shape constructed from them.
- Boss-event reminder (tracker hidden, `bossReminders` on): detection is **passive-only** — Catalyst issues zero boss requests while the tracker is off and relies on Boot.dev's own relayed `boss_events_progress` responses. The toast shows at most once per 24h per event per device; either toast button — or the panel's close (×) button — ends reminders for that event ("Show Tracker" flips the setting via `setFeatureEnabled`, and the `storage.onChanged` live-apply does the rest). In quiet mode `handleBossProgress` never touches `be_boss_state`, so the last tracked event's stats survive until the tracker is re-enabled.
- Maintainer-only reminder test trigger (events are 4–8 weeks apart): set `be_boss_reminder_debug` to `true` in `chrome.storage.local` and reload Boot.dev — a synthetic active event runs through the real `maybeShowBossReminder`, all production guards included. Remove `be_boss_reminder_state` to re-run; unset the flag when done.
- **Cold page loads are server-rendered**: Boot.dev embeds the page's data in the HTML payload and skips the API calls Catalyst listens for (confirmed on Training Grounds and profile pages, 2026-07-15/16). Purely reactive features silently render nothing on F5/direct navigation — they need an explicit request or refresh path for that case. See `ensureProfileUiState` (profile.js) and the entry heal in `trainingGrounds.js`.
- Lesson features (v0.11.0–v0.12.0) are **page-side only** — no API calls, no storage keys, no observers. Each binds one `document` listener in `initEnhancer` and unbinds it in `stopEnhancer`; the feature check happens per event, not per bind, so toggling a setting takes effect on the next click/keypress. The Submit button is identified by exact `Submit` text **plus** a corroborator (`#console-resizer` ancestor, or the `aria-describedby` tooltip mentioning submit) — never by hashed classes, and an unrecognized page fails open to native behavior. Three key choices were rejected on evidence: `Alt+R` for the run shortcut (NVIDIA's GPU-overlay global hotkey swallows the `R` keydown before the page sees it, so it would fail *silently* on those machines); **numpad digits** for the checklist shortcuts (on Windows `Alt`+numpad is the OS character-code input method, e.g. `Alt+0233` → é — the `event.key` fallback only runs when `event.code` is absent, so a numpad press can never match); and `Alt+E` for the answer-side shortcut (`Alt+E`/`Alt+F` open the Chrome/Brave menu on Windows and Linux and are not cancellable from the page).
- Lesson/challenge page anatomy (v0.12.0, probed): `#lesson-container` wraps the whole two-pane view; `#markdown-side` is the lesson-text pane (checklist, prose, **and the Boots chat textarea**); the answer side is whatever is inside the container but outside that pane — the code editor (`div[role="textbox"][contenteditable]`), the Linux terminal, `#interview-side` on interview pages, or a repo-URL `<input>`. All plain ids, no hashed classes. Two gotchas the probes caught: a code page renders **two** `role="textbox"` divs and only the visible one is the editor, and `#markdown-side` also holds two zero-size search inputs — so any answer-side lookup must filter on visibility. Checklists are **not** reliably wrapped in `<details>`: lessons use sections, challenges use a bare `<ul>`/`<ol>`, which is why the checklist is scoped to the pane rather than to section elements (a collapsed `<details>` needs no special case, since its contents fail the visibility test).
- Catalyst's keyboard shortcuts deliberately do **not** step aside for editable targets (changed in v0.12.0; `isEditableTarget` was removed from `utils.js` when its last consumer went). Boot.dev's own `Ctrl+.` works while typing, and the shortcuts are most useful mid-edit. `assignmentShortcuts` additionally binds on the **capture** phase and calls `stopPropagation()` once a target resolves — required to beat the Learn Linux terminal, which writes the digit from its own keydown handler before a bubble-phase listener ever runs. `nextLesson` and `cliShortcuts` stay on the bubble phase without stopping propagation, because they are default-ON and shouldn't fight the page for keys.
- The interceptor (`injected.js`) only rebroadcasts passively-observed responses for the paths the router consumes (`RELAY_PATH_PATTERNS`); keep that allowlist in sync with the router in `content.js`.
- **Training Grounds level filter (v0.13.0 — the premise of v0.10.0 expired).** Boot.dev shipped its own Easy/Medium/Hard filter on 2026-08-01, which made Catalyst's tier pills a duplicate of a native feature. Catalyst now **refines** it instead: it offers the exact levels inside the selected tier, which the native filter cannot do (the maintainer wants only level 10 — worth the most XP — and "hard" spans 8–10). `injected.js` rewrites the `/v1/challenges/search` response before Vue consumes it when a level selection is committed (**fail-open**: any parse/shape problem hands Boot.dev its original response, and records whose level can't be read are never hidden). Because Boot.dev filters server-side *first*, Catalyst now narrows a pre-narrowed set: `d=hard` returns 44 records that are entirely 8–10, of which 14 were level 10 — where the old tier pass could only shrink an already-bounded mixed response.
- **Level pills are offered only while a native tier is selected.** With no tier, the section shows a "Select a difficulty first" empty state (mirroring the native Type section's "Select a language first") and nothing is filtered. This is deliberate: an unfiltered response spreads ~46 records across all ten levels, so a single-level pick there returns a handful of results by nature rather than by defect — a healthy feature that looks broken.
- **How the native tier is resolved**, in two layers: (1) while the popover is open, the native Difficulty **section header icon**, whose `src` swaps to `difficulty_<tier>_icon.<buildhash>.png` when a tier is pending — match the authored stem only, never the hash; (2) otherwise the committed `d=` in the page URL. While the popover is open layer 1 is authoritative *including its negative answer*, because clicking a tier off leaves `d=` stale. **The header icon is the one anchor outside the priority list** — the 2026-08-01 popover diff proved selection lives nowhere else: the native pills carry no `aria-pressed`, no `data-*`, no `role`, only Tailwind color utilities (`border-gray-200` vs `border-gray-600`). It has a fallback and a tripwire; see below. The native section is found by an **exact** match on its `Difficulty` header text, so Catalyst's own section — labelled **"Difficulty Level"** — cannot be mistaken for it. Renaming Catalyst's section to plain "Difficulty" would break tier detection outright.
- Interaction still mirrors the native pills: picks are pending until Boot.dev's **Search** commits them (a capture-phase `submit` listener writes the committed levels into the synchronous `data-be-dl` attribute on `<html>` before the page's own handler can fetch). Boot.dev skips the refetch when q/t/l are unchanged — and **cold loads (F5/deep link) server-render the results with no API call at all** — so `trainingGrounds.js` detects both cases and asks the page to re-run the search via `BE_REFRESH_CHALLENGE_SEARCH` → a page-context Vue-router re-push with a throwaway `be_r` nonce (`location.reload()` last resort). After every search relay, `history.replaceState` strips `be_r` and keeps `dl=<levels>` in the URL matching what actually filtered the results; a `dl=` URL is adopted on load and intersected with the tier `d=` names, so shared links carry the selection between Catalyst users and an incoherent link (`d=easy&dl=10`) filters nothing rather than showing an empty page. Tier bounds now live in **one** copy, `CHALLENGE_TIERS` (trainingGrounds.js) — `injected.js` filters on exact levels and needs no tier concept at all. Evidence bundle: `reference_data/catalyst_versions/v0.13.0_challenge_level_filter/`.
- **The fail-open rule has a sharp edge (v0.12.1).** "Records with unresolvable difficulty are never hidden" means a *renamed field* doesn't fail loudly — it disables the filter while everything still looks healthy: pills toggle, `data-be-dl` sets, `dl=` lands in the URL, and the relay even reports `filtered:true`. Boot.dev's PascalCase→camelCase flip did exactly that. `challengeDifficulty` (injected.js) reads both casings, and `check_challenge_filter.mjs` asserts a camelCase-only record is *filtered* rather than kept. The relay carries `resolvedCount` (how many records yielded a level) and `trainingGrounds.js` warns once when it is 0 of N. `injected.js` also accepts a wrapped response (`{data:[…]}`) so a wrapper appearing later can't disable the filter the same silent way. Diagnosis bundle: `reference_data/catalyst_versions/v0.12.1_training_grounds_filter_repair/`.
- **Three tripwires guard the Training Grounds feature**, one per thing it reads, all `warnOnce`-gated. (1) `tg:level-field` — a filtered response yielded 0 readable levels of N (the v0.12.1 signature). (2) `tg:tier-icon` — the user clicked a native tier that was *not* already selected and the header icon still doesn't report it 400 ms later; deselection is excluded, since no icon is then the correct answer. Without this the pills would silently stop following pending clicks and fall back to `d=`. (3) `tg:row-level` — a results page has challenge rows but none yielded a level from `alt="Difficulty N"`, so the badges stopped rendering.
- **The level badge anchors on `.tooltip-box`, and `aria-describedby` is the wrong hook there** — a rare case where the anchor-priority list points at the worse option. Both the difficulty icon's wrapper *and* the whole result row are tooltip boxes carrying `aria-describedby`, so when Vue reuses a row's DOM and the inner wrapper's attribute isn't assigned yet, `closest()` climbs to the row wrapper (which sits outside the `<a>`) and the badge lands between rows. Caught in v0.13.0 QA as "the first few results have no level". The anchor now rejects any candidate containing the row's `h3`, and each pass sweeps up badges that escaped their row. The pass is also **self-healing rather than incremental**: it inspects the whole row and rebuilds unless exactly one correct badge sits in the right place, so a badge Vue moved, duplicated, or left over from a different challenge is repaired on the next tick instead of persisting.
- **Vue hydration can ADOPT an injected element — the sharpest hazard on a server-rendered page.** A refresh serves SSR HTML that Vue hydrates a moment later, walking the existing DOM **by position**. A level badge inserted before that happens sits exactly where Vue expects its own type-label `<span>`, so Vue claims our element: it overwrites the text with "Code"/"Interview" but *keeps our class*, because it only patches what differs from the vnode it is matching. The row then shows no level and a type label wearing badge styling. It always hits the first rows, because those are the ones still in server-rendered form — later rows were re-created client-side and are safe. Two tells distinguish them in captured markup: SSR nodes keep `<!--[-->` fragment comments and serialize `data-v-*` last, client-created ones do neither. Detection is `badge.textContent !== badge.dataset.beLevel`; the recovery **un-marks the element instead of removing it** (`reclaimAdoptedBadge`), because Vue owns it now and removing it would delete the row's type label until the next re-render. Any future injection into a server-rendered Boot.dev list carries this same risk.
- **Result-row level badges read the DOM on purpose.** The level is printed next to each result's difficulty icon, parsed from that icon's own `alt="Difficulty N"`. Boot.dev renders it identically on API-driven and server-rendered loads, so this is one always-present source; joining the relayed API record by `/challenges/<uuid>` would still need this exact fallback for cold loads (which make no API call) plus a per-page cache. Re-presenting a value the page already shows is the `findTotalStudents` precedent, and a missing value simply renders no badge. `__NUXT_DATA__` was considered and rejected: it does carry every record's difficulty, but at ~793 KB needing devalue index resolution it would only ever back the 10 rows already carrying the number in their markup.
- **Boot.dev's own "Showing 1-10 of 50" line updates itself**, because the rewrite happens before Vue reads the response — no count UI of Catalyst's own is needed. A note reporting what the filter started from was built and removed during v0.13.0 QA: it contradicted the native line (reporting the filtered total where the native line reports the visible page), and native filters explain themselves no further either. Don't re-add one without a concrete complaint to answer.
- **A level selection is only valid for a request that carries its tier — validate against the request, not against remembered state.** `data-be-dl` is tier-prefixed (`hard:8,10`) and `injected.js` applies it only when the outgoing `/v1/challenges/search` URL's own `d=` matches that tier. This exists because Boot.dev drops its difficulty filter through paths Catalyst cannot observe: clearing the search box, running a fresh search with no filters, or navigating back to the catalog all reset it **without opening the popover**, so the cached tier goes stale. Before the guard, a selection made under Hard would filter a later search carrying no `d=` at all — results vanishing with no visible filter to explain them (v0.13.0 QA). Chasing each flow individually is the wrong fix; the request URL is the only synchronous authority.
- **A relayed search can arrive before Catalyst has noticed the navigation.** Browser Back (and the nav-bar Training → Search link) produces no in-page click, so only `content.js`'s 350 ms route scan sees it — and Vue refetches within a few ms of `popstate`. `handleChallengeSearch` therefore re-runs `ensureTrainingGroundsUiState` when the path has changed, *before* judging the response; otherwise it measures the response against the page just left. Related: `syncChallengeSearchUrl` must never delete `dl=` while a committed selection the current tier still backs is waiting on a refresh, or it discards the user's selection on the strength of the very response about to be re-run. Both caught in v0.13.0 QA as "returning to a filtered search drops the level and rewrites the URL".
- **Boot.dev can restore `d=` AFTER the navigation Catalyst adopted.** The nav-bar Training → Search link navigates with no query at all and only then writes its remembered difficulty into the URL from its Vue store. Adopting once per route change therefore saw no tier, restored nothing, and never looked again because the path had stopped changing. `ensureTrainingGroundsUiState` watches a `d=|dl=` key and re-adopts whenever it changes *without* a route change, then heals the rendered results. Note this is safe only because the remembered selection is rewritten on every commit — otherwise re-adopting could resurrect a cleared pick.
- **The selection must survive SPA navigation, because Boot.dev's own filters do.** Boot.dev keeps its difficulty in a Vue store, so leaving the search page and returning restores `d=` — but the URL it rebuilds carries no `dl=`, because it doesn't know that param exists. Adopting that URL therefore dropped Catalyst's selection on every return, and also wiped a selection that had just been committed when a search was started from the catalog page. `rememberedChallengeSelection` (module-level, tab-lifetime, never stored) holds the last committed selection and is restored **only when the route's `d=` still names its tier** — which is what keeps it from resurrecting a filter Boot.dev has dropped. A `dl=` present in the URL always wins; memory only fills a gap. Committing an empty selection overwrites the memory, so clearing the levels genuinely clears them.
- **Two corollaries of the same principle.** The gold dot is driven by what the last relayed search *actually* filtered (`lastChallengeSearch.filtered`), never by the committed selection — otherwise it advertises a filter that isn't in effect, which is what left it lit on the catalog page. And internal navigation (landing ↔ search) **re-adopts from the destination URL** rather than carrying the committed selection across, since the catalog page has no filter at all.
- **The native tier must be read while the popover is OPEN, and remembered.** A Search *click* happens with the popover closed, where the tier can only come from `d=` in the URL — which does not exist yet on a first search and still names the *previous* tier right after a change. `commitChallengeSelection` therefore trusts the `pendingNativeTier` captured by the ensure tick and re-resolves only when the popover is still open (the Enter-in-the-search-box case). Re-resolving unconditionally intersected the selection against an empty tier and wiped it before the attribute was written, so the first search after picking a level silently didn't filter (caught in v0.13.0 QA).
- **Graceful degradation is what makes a rename invisible (v0.12.2).** Every feature here is built to show less rather than break when a value is missing, so a renamed field produces a healthy-looking UI doing nothing. The counterweight is `warnOnce` / `reportUsableFields` (utils.js): cheap boundary checks that log once per session when a non-empty response yields **zero** usable values for a field a feature depends on. Wired into the all-time/daily/karma board handlers, `distillHeatmap`, `handleDashboardContent`, and the challenge-search relay. When adding a feature that reads a new API field, add the corresponding check — that, not more casing fallbacks, is the lesson of v0.12.1. **More fallbacks make this worse:** a cross-semantic fallback (`XPEarned ?? XP` — trailing-24h XP falling back to a *lifetime* total) turns a missing value into a plausible wrong one, which is strictly harder to notice. Those were removed in v0.12.2.
- Training Grounds landing page: Boot.dev added its own search field there (2026-07-30), so a difficulty can be picked before any search exists. Its box is worded differently from the search page's (`placeholder="Search existing challenges"` vs `aria-label="Search Challenges"`), so `isChallengeSearchForm` (trainingGrounds.js) matches the search+challenge word pair in either the label or the placeholder rather than one exact string.
- The opt-in update check hits `api.github.com` (CORS-open, no host permission). The extension still requests only `storage` + `https://www.boot.dev/*`.
- Personal-board daily XP for other users has no exact API source (the daily board is rolling-24h). `leaderboard.js` keeps per-user total-XP snapshots (`record.xpSnapshots`, `[t, xp]` pairs, ≤60, pruned >24.5h) harvested from every response that reveals a total, and `computeDailyXpView` picks the best of: live board value → snapshot-window delta → heatmap estimate → "–". `ESTIMATED_XP_PER_LESSON` (115) is a placeholder awaiting calibration from the maintainer's base-XP spreadsheet — update that one constant when real data lands.
- Personal-board daily karma has **no API source at all** (no daily karma board, nothing to backdate from), so `computeDailyKarmaView` is measured-or-unavailable only: `record.karmaSnapshots` mirrors the XP snapshot store, observed gains display immediately, and a confident 0 needs a ≥30-min watched window (`SNAPSHOT_MIN_WINDOW_MS`). The viewer's own comparison baseline lives in `be_current_user_karma` (storage.local, invalidated on handle change), fed by an own-stats request on leaderboard visits, the top-25 karma board, and passively-observed own **stats** responses (the public profile response has no karma field — confirmed 2026-07-31 — so only `/stats` contributes). All of that requires a known handle, which is why the `findNuxtCurrentUserHandle` fallback matters: without it a fresh install that never opened `/leaderboard` had no baseline and every Daily Karma comparison read unavailable.
- Backup & restore (options page, `backup.js`): the export is versioned JSON (`catalystExport` marker + `BACKUP_FORMAT_VERSION`, independent of the extension version — bump it only on **structural** changes; new settings keys or data sections are not format changes). Sections: `settings` (raw stored object, NOT normalized — unset flags must keep tracking future defaults), `personalLeaderboard` (handles + per-handle xp/karma snapshot series only; profile/stats/heatmap are refetched, never exported), `currentUser` (handle + own karma series; import-guarded to the same handle), `bossState` (`eventId`/`eventHigh`/`eventHighAt`/`allTimeHigh`; event high merges only for the same `eventId`). Import is file-level strict (bad file → nothing written), entry-level lenient (bad handle/point skipped), and everything passes the same sanitizers on the way in. Hand-deleting a section from the JSON skips that section — documented user behavior, keep it working.
