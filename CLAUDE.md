# CLAUDE.md — Agent guidance for catalyst

## What this project is
Browser extension (Manifest V3, Chromium-based browsers — Chrome and Brave; Firefox support is planned) that augments Boot.dev. The browser-loadable directory is `bootdev-extension/`. Everything else (`reference_data/`, `scripts/`, docs) is development support only and is never loaded by the browser.

## File responsibilities

| File | Owns |
|------|------|
| `src/injected.js` | Runs in the page's JS context. Wraps `fetch` and `XMLHttpRequest` to clone `api.boot.dev` JSON responses and relay them to the content script via `window.postMessage`. Also owns the bearer-token replay bridge (`BE_FETCH_JSON`) and `AUTH_REQUIRED_PATHS`/`AUTH_REQUIRED_PATTERNS` — the paths whose requests must be **queued** until an `Authorization` header has been harvested, rather than sent bare and 401'd. No feature logic here. |
| `src/content.js` | Isolated-world content script. `window.postMessage` listener and URL router only. Calls handlers defined in the feature files below. Also owns the `storage.onChanged` listener that live-applies settings (`applyFeatureSettings`) and reloads imported data on the `be_import_broadcast` signal (`applyImportedData`), plus the first-run settings prompt. Must be listed last in `manifest.json`. |
| `src/utils.js` | Shared helpers: `waitFor`, `chromeGet`/`chromeSet` (local) and `chromeGetSync`/`chromeSetSync` (sync), `toast` (severity `variant`, dismiss control, pause-on-hover, `durationMs: 0` = sticky), `escapeHtml`, number formatters, shared constants (`TOP_NAV_BAND_PX`), the dual-casing reader `pickField` (moved here in v0.13.1 when `nextLesson.js` became its second consumer) plus `API_FIELD_ALIASES`/`readField`/`readNum` (v0.14.2 — the explicit PascalCase->camelCase table for leaderboard, profile, stats and heatmap fields, shared by `leaderboard.js` and `profile.js`), and the tripwires `warnOnce`/`reportUsableFields` (renamed field) plus `reportEndpointFailure`/`noteEndpointSuccess` (endpoint that stops answering). A toggle's `desc` is the full explanation shown on the options page; an optional `shortDesc` is what the popup shows instead (one sentence, no caveats) — add it only when the full text is too long to skim. A successful import ends by writing `be_import_broadcast` (storage.local) so open tabs reload the imported keys. Mirrors a few helpers/constants from `utils.js`/`leaderboard.js`/`boss.js`, each marked "keep in sync". |

Also owns the boss-event reminder toast (`bossReminders`) shown when the tracker is hidden and an event is live. |
| `src/nextLesson.js` | Next Lesson top-nav link and Alt+N keyboard shortcut. |
| `src/submitConfirm.js` | Optional confirmation before a code-lesson submission (`submitConfirm`, default-off). The guard fires only on `event.isTrusted && event.detail > 0`, which scopes it to pointer clicks, leaves `Ctrl+Shift+Enter` alone, and makes the confirm-path `.click()` (untrusted) impossible to re-intercept — no bypass flag, no recursion. Also owns the v0.14.1 **risk gate**: the dialog is suppressed when a failed submission can no longer cost anything — `successCount > 0` **or** `armorUsedAt` set, both from `/v1/users/lessons/{uuid}`, cached in `lessonRiskFreeByUuid` (in memory, tab-lifetime, **never storage**). Unknown means the dialog shows. |
| `src/cliShortcuts.js` | CLI command copy shortcuts: `Alt+C` copies `bootdev run <uuid>`, `Alt+Shift+C` copies it with `-s`. Route UUID and displayed commands are read **at keypress time** — nothing cached, observed, or stored. Capability comes from what the page renders (a safe submit-only lesson has no run command, and one is never derived by editing the submit command). Clipboard via `navigator.clipboard.writeText` under the keypress gesture; no permission needed. |
| `src/assignmentShortcuts.js` | Checklist keyboard shortcuts (`assignmentShortcuts`, default-off): `Alt+1`–`Alt+9` toggle the matching top-level step, `Alt+0` checks the next unfinished box, `Alt+`` returns focus to the answer side. Works on `/lessons/<uuid>` **and** `/challenges/<uuid>` (`lessonOrChallengeUuidFromPath`). Everything is read at keypress time — no cache, no observers, no storage. The checklist is scoped to `#markdown-side` and the answer side is everything in `#lesson-container` outside it; hierarchy is modelled by one rule (a step is top-level when its **nearest** `<li>` has no `<li>` ancestor). Capture-phase listener that stops propagation only once a target resolves, which is what lets it beat the course terminal to the keystroke. |
| `src/trainingGrounds.js` | Training Grounds difficulty **level** filter: a "Difficulty Level" section injected into the challenge-search filter popover offering the exact levels inside whichever tier Boot.dev's own difficulty filter has selected (Hard → 8/9/10). The committed state is per-tab, carried in the page URL (`dl=`), handed to `injected.js` via the `data-be-dl` attribute, and never stored. The response filtering itself lives in `injected.js`. |
| `src/styles.css` | All injected UI styles. Uses `be-` prefix on all class names to avoid clashing with Boot.dev's own styles. |
| `assets/` | Bundled static art (loaded by the browser, unlike `reference_data/`). `frames/0.png`–`9.png` are avatar role frames indexed to `ROLE_FRAME_INDEX_BY_ROLE` in `leaderboard.js`, loaded into the page via `chrome.runtime.getURL` + `web_accessible_resources` (`use_dynamic_url`) as the fallback when the API gives no frame URL. `maptexture2.webp` is the boss-panel + settings-page background: `boss.js` resolves the injected panel's URL with `chrome.runtime.getURL` and passes it through `--be-boss-texture`, while `popup.css` can reference the asset relatively because it runs on an extension page. Both are copies of Boot.dev art, bundled with Boot.dev's permission — see `ATTRIBUTION.md`. |
| `manifest.json` | MV3 manifest. Do not add permissions without explaining why. Current permissions: `storage` only (covers both `storage.local` and `storage.sync`). Declares `action.default_popup` (popup.html) and `options_ui` (options.html). |

## Architecture rule (DOM scraping is a last resort)
Boot.dev is a Nuxt/Vue SPA. Its CSS class names are hashed and rebuilt on every redeploy. **Avoid reading data by scraping the DOM unless absolutely necessary.** As much data as possible must come from intercepted API responses; the DOM is primarily for locating injection anchors and writing UI. When a value has no API source at all (e.g., the platform-wide student count, which Boot.dev only server-renders into the page payload), reading it from rendered text is acceptable as a last resort — match on stable text landmarks, never hashed classes, and read only the minimum needed. See `src/leaderboard.js` `findTotalStudents` for the canonical example, and `findNuxtCurrentUserHandle` (same file) for the other sanctioned case: the signed-in user's own handle, which has no API source because every user endpoint requires already knowing the handle. That one parses `#__NUXT_DATA__` (devalue: a flat array where each field value is an *index* into it) at most once per page load, because the payload runs to hundreds of KB and the DOM scan ticks every 2 seconds.

Interception flow:
```
page fetch/XHR → injected.js (page context) → window.postMessage → content.js router → feature handlers
```

## Injection anchor priority
When finding where to inject UI elements, prefer stable hooks in this order:
1. Element `id`
2. `data-*` attributes
3. `aria-*` attributes
4. Semantic HTML tags
5. Visible text content landmarks
6. CSS class names — if used, add a `// FRAGILE: hashed class, may break on redeploy` comment

## Content script load order
Files share a single global scope — no ES module syntax (`import`/`export`), no build step, no bundler. `manifest.json` loads them in order:

```
utils.js → settings-schema.js → settings.js → leaderboard.js → profile.js → boss.js → nextLesson.js → updateCheck.js → trainingGrounds.js → submitConfirm.js → cliShortcuts.js → assignmentShortcuts.js → content.js
```

`utils.js` first so helpers are available everywhere; `settings-schema.js` next so the shared defaults/labels exist; `settings.js` after that so `isFeatureEnabled`/`isComparisonEnabled` are available to every feature. `content.js` last so the router can call handlers already defined by the feature files.

(`popup.js` runs in the extension-page context, not the content-script scope, so it can't see the feature files — but it loads `src/settings-schema.js` via its own `<script>` tag, so the popup and the content script share exactly one copy of the defaults, labels, and board ordering. Keep the settings key string (`be_settings`) aligned between `popup.js` and `settings.js`.)

## Conventions
- `FIXME` comments mark field names inferred from context that should be verified against real API responses in `reference_data/`.
- `chrome.storage.local` keys for boss data: `be_boss_state` (tracker stats — aura highs plus `observedSince`, `xpUser` and the chest ladder, the selected `guild` and `pinnedGuildId`, the `aura` statistics, `alerts`/`lastAlert` bookkeeping, and the `previousEvent` archive), `be_boss_ui_state` (panel position/minimized, and the per-device aura-alert floor), `be_boss_reminder_state` (reminder bookkeeping, per-device), `be_boss_inactive_notice` (last "no active event" toast timestamp), `be_boss_debug_response` (maintainer-only replay body, see below). The Training Grounds level selection is deliberately **never written to storage** — it is per-tab and carried in the page URL (`dl=8,10`, alongside Boot.dev's own `d=hard`), matching how the native filters derive from the URL. Its one piece of memory is `rememberedChallengeSelection`, a module-level variable in `trainingGrounds.js` that lives only as long as the tab; see the SPA-navigation bullet below for why it exists and why it cannot resurrect a dropped filter. Feature settings live in `chrome.storage.sync` under `be_settings`. The Submit confirmation's lesson-risk cache is deliberately **not** a storage key — it is an in-memory `Map` for the tab's lifetime, because the data is trivially re-fetchable and a stale copy would only ever be re-derived. `be_import_broadcast` (storage.local) is the import signal: written by `backup.js` after a successful options-page import, consumed by `content.js` to reload imported keys in open tabs — tabs deliberately do NOT react to the data keys themselves, because they write those keys routinely and would loop on their own writes.
- Gate any new feature behind a flag in `settings-schema.js` (`SETTINGS_DEFAULTS`, default-on; the four exceptions are `versionCheck`, default-off because it can reach off-device, `bossTracker`, default-off because the panel must be quiet until the user opts in, `submitConfirm`, default-off because it interposes a step in front of a native Boot.dev action, and `assignmentShortcuts`, default-off because it claims ten Alt+digit combinations even while the user is typing; `bossAuraAlerts` is default-ON but inert while `bossTracker` is off) and a toggle rendered from `FEATURE_TOGGLES`/`PERSONAL_BOARD_TOGGLES`/`COMPARISON_BOARDS`; check `isFeatureEnabled`/`isComparisonEnabled`/`isPersonalBoardEnabled` at its render/request entry and tear down cleanly when off. Because the schema is shared, adding a key in one place covers both the content script and the settings pages.
- All injected DOM elements use the `be-` CSS class prefix.
- Do not add `console.log` for debugging; use `console.debug` so it can be filtered.

## API endpoints used (summary)

**The v0.12.2 audit read live and field-checked all 11 concrete endpoint variants Catalyst uses on 2026-07-31** (bundle: `reference_data/catalyst_versions/v0.12.2_api_casing_audit/`). The bullets below summarize them by route family, so one bullet may cover multiple concrete variants and `/v1/leaderboard_xp/day` is repeated to document its special personal-board role. On that date only `/v1/challenges/search` and `/v1/boss_events_progress` served camelCase. **That is no longer the shape of the leaderboard/profile API: as of 2026-08-19 the endpoints re-read for v0.14.2 were camelCase** — both global XP and karma boards, both league boards, `/v1/users/public/{h}`, `/stats` and `/activity_heatmap`, measured per field. Endpoints not re-read that day are not covered by that observation. Boot.dev migrates casing **per DTO, not globally** — the same page payload carries a PascalCase user object next to camelCase achievement objects — so assume any single endpoint can flip on its own schedule and never assume a global switch. Catalyst reads **both** spellings everywhere rather than migrating, because casing has moved in both directions before.

**Auth:** `/v1/boss_events_progress`, `/v1/dashboard_content`, and **both `/v1/league_leaderboard_xp/*` boards** return 401 to a cookie-only request; they need the `Authorization` header `injected.js` harvests from Boot.dev's own traffic. `/v1/users/lessons/{uuid}` also 401s and is queued alongside them. All are in `AUTH_REQUIRED_PATHS`/`AUTH_REQUIRED_PATTERNS` so a request made before a header is seen is queued, not sent bare. Every other endpoint works on the session cookie alone — **except `/v1/course_progress_by_lesson/{uuid}`, which does not 401 at all.** It answers **200 with an un-personalised body** (every `isComplete` false; measured 2026-08-15 as 0 of 168 against 167 of 168 with a token), which no status code reveals. Catalyst no longer requests it, so it is not queued; anything that starts requesting it must add it back. A silent lie is harder to notice than a 401 — check what an endpoint returns *without* the token before assuming cookie auth is enough.

- `/v1/leaderboard_xp/{period}` and `/v1/league_leaderboard_xp/{period}` — leaderboard data; period = day | week | month (**global `alltime` was REMOVED 2026-08-14** — it returns 400 `{"error":"Invalid timeframe"}`; 23 candidate period names were tested and no replacement timeframe was found. The league board still answers `alltime`). The `day` boards are **rolling last-24-hours** windows (user-reported), and their entries carry both `XPEarned` (trailing-24h XP) and `XP` (lifetime total). `XPEarned` for a given handle is identical on the global and league daily boards (verified 2026-07-31), which is what makes the league board a valid fallback. **`TotalXP` does not exist** on any leaderboard entry — nor do `IsCurrentUser`/`IsSelf`/`IsMe`. On the all-time board `XPEarned` ≈ `XP` but is not always exactly equal (24 of 25 matched on 2026-07-31)
- `/v1/users/public/{username}` — public profile; cumulative XP is at `data.XP`. **Carries no karma field in any casing** — karma comes from `/stats` only, so a tracked user's karma series advances on `/stats` refreshes and karma-board sightings, never on a profile fetch
- `/v1/users/public/{username}/stats` — public stats including karma
- `/v1/users/public/{username}/activity_heatmap?timezone={IANA}` — per-day activity counts (`data.Calendar`; includes 0-XP resubmits) plus a separate `data.GithubCommits` series (streak-only, no XP); feeds the personal daily-XP estimate tier
- `/v1/boss_events_progress` — boss tracker source of truth; new-event detection keys off `Event.UUID`
- `/v1/dashboard_content` — Next Lesson source via `CurrentLessonUUID`/`currentLessonUUID`. **Entirely camelCase as of 2026-08-15**; `nextLesson.js` reads both casings per field through `pickField`, including `chapters[].lessons[].{uuid,isRequired,isComplete,isReset}` in the `currentCourseProgress` fallback tier
- `/v1/leaderboard_xp/day` — exact personal-board daily XP when a handle appears there; every sighting also yields a backdated total-XP snapshot (`XP − XPEarned` at now−24h)
- `/v1/challenges/search` — Training Grounds challenge search (`q` required, `t`/`l`/`d` optional); one response carries the complete result array (bare JSON array, no count metadata; the page paginates it locally 10/page), and `topics.difficulty` (1–10) drives the Catalyst level filter. **`d=easy|medium|hard` is Boot.dev's own server-side tier filter, added 2026-08-01** — one value at a time, bounds confirmed exactly (easy 1–4, medium 5–7, hard 8–10, zero leakage across four captures). Catalyst reads `d` and never writes it. **Casing warning:** this response was PascalCase (`Topics.Difficulty`) on 2026-07-14 and camelCase (`topics.difficulty`) by 2026-07-30 — `challengeDifficulty` (injected.js) reads both

- `/v1/users/lessons/{uuid}` — per-lesson history for the signed-in user, and the **only** source the Submit confirmation needs. **Fetched by Boot.dev on every lesson navigation** (17 of 17, 15 of 15, 14 of 14 across three HARs), so it is normally read passively; Catalyst requests it only when a lesson's state is still unknown. Carries no `isComplete` in any casing — instead, `successCount > 0` (completed at least once) or `armorUsedAt` set (armor already spent here) directly answers Catalyst's risk gate: either persistent condition means a failed submission can no longer cost anything. **Neither field is cleared by a reset**, which is why the risk decision can be made without reading current `isComplete`/`isReset` course progress. `previousSubmissionCode` is cleared by a reset and is deliberately NOT read (see the risk-gate note below). Measured 2026-08-18
- `/v1/course_progress_by_lesson/{uuid}` — lesson completion for the **whole course** the uuid belongs to (168 lessons in the 2026-08-15 capture), camelCase: `chapters[].lessons[].{uuid,title,isRequired,isComplete,isReset}`. Relayed and routed as a dashboard-refresh signal, but **no feature reads its body** as of v0.14.1. `dashboard_content.currentCourseProgress` carries the identical block for the *current* course only. **Needs the bearer token but does not 401** — see the Auth note above, and add it back to `AUTH_REQUIRED_PATTERNS` before requesting it.

Confirmed API response field names are documented in `reference_data/bootdev_api_info/bootdev_openapi.yaml`

## Notes

- Boss chest tier names are inferred from the rendered modal order because `boss_events_progress` contains chest UUIDs and thresholds, not display names.
- Alerts are in-page toasts; the extension does not request the browser's `"notifications"` permission.
- **The All-Time panel renders only from a board received in the current session (v0.13.1).** `loadCachedAllTimeLeaderboard` restores `be_alltime_leaderboard_cache` into `storedAllTimeCache`, which nothing renders or compares against; `cachedAllTimeEntries` is filled only by `handleAllTimeLeaderboard`, i.e. only by a 200. Since nothing fills it, the panel simply never appears and `getMyValue("xp")` falls through to the live league boards. Fixing the *writer* rather than each reader is what makes the panel, the ensure pass, the comparisons and the snapshot harvest all honest at once. Catalyst also **stops requesting the timeframe** (`ALLTIME_TIMEFRAME_AVAILABLE = false` in `requestAllTimeLeaderboardData`): it was the only consumer, so the request could only ever put a red 400 in the console. The handler and render path are intact, so flipping that constant resumes probing. **Do not delete `be_alltime_leaderboard_cache`**: it is the seed candidate for the v0.15.0 rebuild.
- **The boss panel renders the v0.14.0 event model.** Boot.dev replaced the community boss goal with individual + guild progress on 2026-08-14, all inside the same `/v1/boss_events_progress` response (`guilds[]` and `guildRewardGranted` were added; no separate guild endpoint was found — eleven plausible endpoint names returned 404 with a valid token). The panel is three blocks: **aura** (current / event high / all-time high / event average / below event high / lessons this hour), **your fight** (`xpUser` against the sorted `userXPThreshold` ladder, gold bar, next chest named, collapsing to `Boss defeated · Mythic chest earned` when all four are earned), and **one guild** (`selectBossGuild`). Nothing is derived from `xpTotal` or from `healthPoints`-as-community-HP: `healthPoints` now carries the personal 10000 target and `rewards[].xpThreshold` equals `userXPThreshold`. Chest state is computed from `xpUser` vs `userXPThreshold` and reads **neither** `isUnlocked` nor `isUnlockedByUser` — captures on 2026-08-16 show they flip per chest and agree (at `xpUser` 2689 the 2500 reward was `true` while the rest were `false`, with community `xpTotal` above 100M), so the computation now matches the flags rather than working around them. **Guild XP is the sum of QUALIFIED members' full event XP, applied retroactively, and reported as 0 below 2 qualified contributors** (measured: a guild sat at 0 while one member held 260k, then jumped to `0 → 6149` where 3045 + 3104 = 6149 exactly). The panel says so rather than showing a bare 0. `contributorCount` is the qualified count (Boot.dev renders it as "N of M members qualified"); the threshold is consistent with `20000 + 5000 × max(0, qualified − 2)` but is **read, never derived**.
- **An injected stylesheet inherits the page's CSS reset, so injected elements must state their own `display`.** Boot.dev's reset sets `svg { display: block }` (Tailwind Preflight does exactly this), which put the boss panel's info marker on a line of its own and broke it out of a `white-space: nowrap` button — a line break inline content cannot produce, which is what identifies the cause. `.be-boss-info` now declares `display: inline-block`. Element defaults are not safe assumptions inside a content script; a class selector beats the page's element selector, so stating it explicitly is enough.
- **Bundled images referenced from `styles.css` must be resolved through `chrome.runtime.getURL`, not a relative `url()`.** A relative path in the content-script stylesheet resolved against the *document* (measured 2026-08-14: `url("https://www.boot.dev/assets/maptexture2.webp")`, which 404s), so the boss panel had been rendering with no texture. `boss.js` now sets `--be-boss-texture` from `BOSS_TEXTURE_URL` and the CSS falls back to `none`. `popup.css` is unaffected — extension pages resolve relative paths correctly.
- **Avatars are reconciled by signature (v0.13.1).** `patchPersonalRow`/`patchAllTimeCard` patch rows in place so the current-user glow never re-mounts, and they used to leave the `.be-leader-avatar` subtree frozen at its first render — so a row drawn before its profile arrived (fresh install, or straight after a backup import, which carries handles and snapshots but not profiles) kept a silhouette and no frame until a reload. `leaderAvatarSignature` (avatar URL + frame URL + frame index + display name) is stamped on the span as `data-be-avatar-sig`, and `patchLeaderAvatar` rebuilds only that subtree when it changes. Any future in-place patcher needs the same treatment for whatever it doesn't touch.
- Per-event boss stats reset automatically when `Event.UUID` changes. The all-time high persists across events, and the outgoing event is archived first (`archivePreviousEvent` → `state.previousEvent`: final chests, guild result, observed high and average), because events are 4–8 weeks apart and the record would otherwise be unanswerable the moment a new one starts. A finished event keeps its numbers on screen behind a `Final — event ended …` banner; the archive shows as one line in the panel's settings.
- **Guild selection is pinned per event.** No completed guild → the eligible one closest to completing (least remaining XP), re-evaluated every response. A completed guild → that one, **pinned** (most XP, then UUID, so the first choice is deterministic), so a second guild completing later never switches the display. The pin resets with the event, and a pin naming a guild that has vanished (the user left it) is cleared and the rule re-runs.
- **Aura statistics and alerts (v0.14.0).** `state.aura` holds a **time-weighted** mean over *observed* time: each response contributes the elapsed interval, capped at 5 minutes, at the value that was live across it — so a closed browser cannot weight one value by three days, and the mean matches the panel's "Observed since" claim. The mean is hidden below 30 minutes observed. `changes` logs ≥1-point steps, capped at 500; because the mean is an O(1) aggregate, that cap never distorts it. Four alert tiers (`chooseAuraAlert`, pure): record → event high → near the high (≥80% of it) → above average (+10). Highest match only, one per aura change, per-tier cooldowns (10/10/60/120 min), and a lower tier stays quiet for 15 minutes after a higher one. The `prev… > 0` guards stop a fresh install treating its first sighting as a record. Alerts are toasted **and** written to a panel line that ages out after 3 hours or is dismissed — a toast is missable, the panel is not. Gated by `bossAuraAlerts`. The floor ("Min aura to alert %", default 40) lives in `be_boss_ui_state` per device, and is read through an explicit `== null` check: `num(null)` is 0, so reading it through `num()` made the default unreachable and every alert ran with no floor.
- **The tracker records while it is switched off.** Quiet mode issues zero requests (`requestBossProgress` refuses) and shows no UI, but it processes Boot.dev's own relayed responses into `be_boss_state`. This replaced the pre-v0.14.0 guarantee that quiet mode never wrote at all — which is why an event that peaked at 100% was recorded as 66%. Consequence: **`loadBossState` must run regardless of the setting** (it does, from `restoreBossPanel`), because a write from a null in-memory copy would create a fresh record and destroy `allTimeHigh`.
- Boss polling stops between events: a response whose `Event.ExpiresAt` is in the past marks the event inactive, halts the 2-min poll, and shows a "no active event" toast at most once per 24h per device (timestamp in `be_boss_inactive_notice`, storage.local). A response with **no readable event identity** (`Event.UUID`/`Event.StartsAt` both absent after normalization) also counts as inactive: it must never trigger the reminder toast (the missing-expiry fail-open used to make it look "active") and never resets the stored per-event stats. A forced re-check (navigation, manual Refresh, tab focus) or Boot.dev's own passive `boss_events_progress` fetch resumes polling when a new event starts.
- **Boss casing — this endpoint is mid-migration and the normalizer is load-bearing today.** The live-event capture (2026-06-26) is PascalCase; between-events captures on **2026-07-16 and 2026-07-31** are entirely camelCase (`event.uuid`, `xpBonus`). `normalizeBossProgressJson` (boss.js) maps camelCase onto the PascalCase names the rest of the file reads. As of v0.12.2 it reads **per field** via `pickField(obj, Pascal, camel)` (in `utils.js` since v0.13.1) rather than gating on the shape of the whole response. The old gate bailed out whenever `Event` was present, so a **mixed** response (a live event restoring `Event` while leaving `xpBonus` camel) would have passed through without normalizing `XPBonus`; the `cur.bonusPct != null` guard would then have skipped the aura write while still allowing the updated timestamp to render. No mixed production response has been captured. `scripts/check_boss_normalizer.mjs` pins the captured shapes plus a synthetic mixed shape, and drives the v0.14.0 helpers against the live captures taken during the 2026-08 event (partial ladder, both qualification transitions, a completed guild beside a mid-progress one).
- Boss-event reminder (tracker hidden, `bossReminders` on): detection is **passive-only** — Catalyst issues zero boss requests while the tracker is off and relies on Boot.dev's own relayed `boss_events_progress` responses. The toast shows at most once per 24h per event per device; either toast button — or the panel's close (×) button — ends reminders for that event ("Show Tracker" flips the setting via `setFeatureEnabled`, and the `storage.onChanged` live-apply does the rest). In quiet mode `handleBossProgress` still records into `be_boss_state` (see above) but renders nothing.
- Maintainer-only: `be_boss_debug_response` (storage.local) replays a captured `/v1/boss_events_progress` body — probe 01d's wrapper or a bare body — through the **real** `handleBossProgress` on load, which is the only way to exercise the panel and the alert tiers between events. Keep the live event's `uuid` in the replayed body or it reads as a new event and resets the per-event stats. Reminder test trigger (events are 4–8 weeks apart): set `be_boss_reminder_debug` to `true` in `chrome.storage.local` and reload Boot.dev — a synthetic active event runs through the real `maybeShowBossReminder`, all production guards included. Remove `be_boss_reminder_state` to re-run; unset the flag when done.
- **Cold page loads are server-rendered**: Boot.dev embeds the page's data in the HTML payload and skips the API calls Catalyst listens for (confirmed on Training Grounds and profile pages, 2026-07-15/16). Purely reactive features silently render nothing on F5/direct navigation — they need an explicit request or refresh path for that case. See `ensureProfileUiState` (profile.js) and the entry heal in `trainingGrounds.js`.
- Lesson features (v0.11.0–v0.12.0) are **page-side only** — no storage keys, no observers, and (with one exception) no API calls. The exception is `submitConfirm`'s risk gate (v0.14.1), which needs a value the page does not render: it requests `/v1/users/lessons/{uuid}` at most once per lesson per tab, only while the default-off setting is on, and only when that lesson's state is not already cached. Boot.dev fetches that endpoint on every lesson navigation, so the request only ever covers what its own traffic misses — a cold load, which is server-rendered and may make no API call at all. Each binds one `document` listener in `initEnhancer` and unbinds it in `stopEnhancer`; the feature check happens per event, not per bind, so toggling a setting takes effect on the next click/keypress. The Submit button is identified by exact `Submit` text **plus** a corroborator (`#console-resizer` ancestor, or the `aria-describedby` tooltip mentioning submit) — never by hashed classes, and an unrecognized page fails open to native behavior. Three key choices were rejected on evidence: `Alt+R` for the run shortcut (NVIDIA's GPU-overlay global hotkey swallows the `R` keydown before the page sees it, so it would fail *silently* on those machines); **numpad digits** for the checklist shortcuts (on Windows `Alt`+numpad is the OS character-code input method, e.g. `Alt+0233` → é — the `event.key` fallback only runs when `event.code` is absent, so a numpad press can never match); and `Alt+E` for the answer-side shortcut (`Alt+E`/`Alt+F` open the Chrome/Brave menu on Windows and Linux and are not cancellable from the page).
- Lesson/challenge page anatomy (v0.12.0, probed): `#lesson-container` wraps the whole two-pane view; `#markdown-side` is the lesson-text pane (checklist, prose, **and the Boots chat textarea**); the answer side is whatever is inside the container but outside that pane — the code editor (`div[role="textbox"][contenteditable]`), the Linux terminal, `#interview-side` on interview pages, or a repo-URL `<input>`. All plain ids, no hashed classes. Two gotchas the probes caught: a code page renders **two** `role="textbox"` divs and only the visible one is the editor, and `#markdown-side` also holds two zero-size search inputs — so any answer-side lookup must filter on visibility. Checklists are **not** reliably wrapped in `<details>`: lessons use sections, challenges use a bare `<ul>`/`<ol>`, which is why the checklist is scoped to the pane rather than to section elements (a collapsed `<details>` needs no special case, since its contents fail the visibility test).
- Catalyst's keyboard shortcuts deliberately do **not** step aside for editable targets (changed in v0.12.0; `isEditableTarget` was removed from `utils.js` when its last consumer went). Boot.dev's own `Ctrl+.` works while typing, and the shortcuts are most useful mid-edit. `assignmentShortcuts` additionally binds on the **capture** phase and calls `stopPropagation()` once a target resolves — required to beat the Learn Linux terminal, which writes the digit from its own keydown handler before a bubble-phase listener ever runs. `nextLesson` and `cliShortcuts` stay on the bubble phase without stopping propagation, because they are default-ON and shouldn't fight the page for keys.

- **Training Grounds level filter (v0.13.0 — the premise of v0.10.0 expired).** Boot.dev shipped its own Easy/Medium/Hard filter on 2026-08-01, which made Catalyst's tier pills a duplicate of a native feature. Catalyst now **refines** it instead: it offers the exact levels inside the selected tier, which the native filter cannot do (the maintainer wants only level 10 — worth the most XP — and "hard" spans 8–10). `injected.js` rewrites the `/v1/challenges/search` response before Vue consumes it when a level selection is committed (**fail-open**: any parse/shape problem hands Boot.dev its original response, and records whose level can't be read are never hidden). Because Boot.dev filters server-side *first*, Catalyst now narrows a pre-narrowed set: `d=hard` returns 44 records that are entirely 8–10, of which 14 were level 10 — where the old tier pass could only shrink an already-bounded mixed response.
- **Level pills are offered only while a native tier is selected.** With no tier, the section shows a "Select a difficulty first" empty state (mirroring the native Type section's "Select a language first") and nothing is filtered. This is deliberate: an unfiltered response spreads ~46 records across all ten levels, so a single-level pick there returns a handful of results by nature rather than by defect — a healthy feature that looks broken.
- **How the native tier is resolved**, in layers: (1) while the popover is open, the native Difficulty pills' own **`aria-pressed`** state, matched to the pressed pill's label; (2) failing that, the section **header icon**, whose `src` swaps to `difficulty_<tier>_icon.<buildhash>.png` when a tier is pending — match the authored stem only, never the hash; (3) otherwise the committed `d=` in the page URL. While the popover is open layers 1–2 are authoritative *including their negative answer*, because clicking a tier off leaves `d=` stale. **`aria-pressed` did not exist when this was built** — the 2026-08-01 popover diff recorded that selection lived nowhere but Tailwind color utilities (`border-gray-200` vs `border-gray-600`), and Boot.dev added the attribute at some point before the 2026-08-15 capture. The icon read is kept as the fallback, and there is a tripwire; see below. The native section is found by an **exact** match on its `Difficulty` header text, so Catalyst's own section — labelled **"Difficulty Level"** — cannot be mistaken for it. Renaming Catalyst's section to plain "Difficulty" would break tier detection outright.
- Interaction still mirrors the native pills: picks are pending until the search runs, which writes the committed levels into the synchronous `data-be-dl` attribute on `<html>` before the page's own handler can fetch. **The commit trigger is a capture-phase `keydown` on `document` (Enter in the search box), not the form's `submit` event** — Boot.dev removed the Search button and pressing Enter emits no `submit` at all (probe 06, 2026-08-14: keydown → `history.replaceState` → fetch, nothing in between), which silently stopped every commit in v0.13.x. The `submit` listener is kept alongside it so an Apply button would start working on its own; both firing is harmless because `commitChallengeSelection` is idempotent. The keydown never calls `preventDefault`/`stopPropagation` — Boot.dev's own search must run exactly as it would have. Boot.dev skips the refetch when q/t/l are unchanged — and **cold loads (F5/deep link) server-render the results with no API call at all** — so `trainingGrounds.js` detects both cases and asks the page to re-run the search via `BE_REFRESH_CHALLENGE_SEARCH` → a page-context Vue-router re-push with a throwaway `be_r` nonce (`location.reload()` last resort). After every search relay, `history.replaceState` strips `be_r` and keeps `dl=<levels>` in the URL matching what actually filtered the results; a `dl=` URL is adopted on load and intersected with the tier `d=` names, so shared links carry the selection between Catalyst users and an incoherent link (`d=easy&dl=10`) filters nothing rather than showing an empty page. Tier bounds now live in **one** copy, `CHALLENGE_TIERS` (trainingGrounds.js) — `injected.js` filters on exact levels and needs no tier concept at all. Evidence bundle: `reference_data/catalyst_versions/v0.13.0_challenge_level_filter/`.
- **The fail-open rule has a sharp edge (v0.12.1).** "Records with unresolvable difficulty are never hidden" means a *renamed field* doesn't fail loudly — it disables the filter while everything still looks healthy: pills toggle, `data-be-dl` sets, `dl=` lands in the URL, and the relay even reports `filtered:true`. Boot.dev's PascalCase→camelCase flip did exactly that. `challengeDifficulty` (injected.js) reads both casings, and `check_challenge_filter.mjs` asserts a camelCase-only record is *filtered* rather than kept. The relay carries `resolvedCount` (how many records yielded a level) and `trainingGrounds.js` warns once when it is 0 of N. `injected.js` also accepts a wrapped response (`{data:[…]}`) so a wrapper appearing later can't disable the filter the same silent way. Diagnosis bundle: `reference_data/catalyst_versions/v0.12.1_training_grounds_filter_repair/`.
- **Three tripwires guard the Training Grounds feature**, one per thing it reads, all `warnOnce`-gated. (1) `tg:level-field` — a filtered response yielded 0 readable levels of N (the v0.12.1 signature). (2) `tg:tier-anchor` — the user clicked a native tier that was *not* already selected and **neither** `aria-pressed` nor the header icon reports it 400 ms later; deselection is excluded, since no tier is then the correct answer. Without this the pills would silently stop following pending clicks and fall back to `d=`. (3) `tg:row-level` — a results page has challenge rows but none yielded a level from `alt="Difficulty N"`, so the badges stopped rendering.
- **The level badge anchors on `.tooltip-box`, and `aria-describedby` is the wrong hook there** — a rare case where the anchor-priority list points at the worse option. Both the difficulty icon's wrapper *and* the whole result row are tooltip boxes carrying `aria-describedby`, so when Vue reuses a row's DOM and the inner wrapper's attribute isn't assigned yet, `closest()` climbs to the row wrapper (which sits outside the `<a>`) and the badge lands between rows. Caught in v0.13.0 QA as "the first few results have no level". The anchor now rejects any candidate containing the row's `h3`, and each pass sweeps up badges that escaped their row. The pass is also **self-healing rather than incremental**: it inspects the whole row and rebuilds unless exactly one correct badge sits in the right place, so a badge Vue moved, duplicated, or left over from a different challenge is repaired on the next tick instead of persisting.
- **Vue hydration can ADOPT an injected element — the sharpest hazard on a server-rendered page.** A refresh serves SSR HTML that Vue hydrates a moment later, walking the existing DOM **by position**. A level badge inserted before that happens sits exactly where Vue expects its own type-label `<span>`, so Vue claims our element: it overwrites the text with "Code"/"Interview" but *keeps our class*, because it only patches what differs from the vnode it is matching. The row then shows no level and a type label wearing badge styling. It always hits the first rows, because those are the ones still in server-rendered form — later rows were re-created client-side and are safe. Two tells distinguish them in captured markup: SSR nodes keep `<!--[-->` fragment comments and serialize `data-v-*` last, client-created ones do neither. Detection is `badge.textContent !== badge.dataset.beLevel`; the recovery **un-marks the element instead of removing it** (`reclaimAdoptedBadge`), because Vue owns it now and removing it would delete the row's type label until the next re-render. Any future injection into a server-rendered Boot.dev list carries this same risk.
- **Result-row level badges read the DOM on purpose.** The level is printed next to each result's difficulty icon, parsed from that icon's own `alt="Difficulty N"`. Boot.dev renders it identically on API-driven and server-rendered loads, so this is one always-present source; joining the relayed API record by `/challenges/<uuid>` would still need this exact fallback for cold loads (which make no API call) plus a per-page cache. Re-presenting a value the page already shows is the `findTotalStudents` precedent, and a missing value simply renders no badge. `__NUXT_DATA__` was considered and rejected: it does carry every record's difficulty, but at ~793 KB needing devalue index resolution it would only ever back the 10 rows already carrying the number in their markup.
- **Boot.dev's own "Showing 1-10 of 50" line updates itself**, because the rewrite happens before Vue reads the response — no count UI of Catalyst's own is needed. A note reporting what the filter started from was built and removed during v0.13.0 QA: it contradicted the native line (reporting the filtered total where the native line reports the visible page), and native filters explain themselves no further either. Don't re-add one without a concrete complaint to answer.
- **A level selection is only valid for a request that carries its tier — validate against the request, not against remembered state.** `data-be-dl` is tier-prefixed (`hard:8,10`) and `injected.js` applies it only when the outgoing `/v1/challenges/search` URL's own `d=` matches that tier. This exists because Boot.dev drops its difficulty filter through paths Catalyst cannot observe: clearing the search box, running a fresh search with no filters, or navigating back to the catalog all reset it **without opening the popover**, so the cached tier goes stale. Before the guard, a selection made under Hard would filter a later search carrying no `d=` at all — results vanishing with no visible filter to explain them (v0.13.0 QA). Chasing each flow individually is the wrong fix; the request URL is the only synchronous authority.
- **A relayed search can arrive before Catalyst has noticed the navigation.** Browser Back (and the nav-bar Training → Search link) produces no in-page click, so only `content.js`'s 350 ms route scan sees it — and Vue refetches within a few ms of `popstate`. `handleChallengeSearch` therefore re-runs `ensureTrainingGroundsUiState` when the path has changed, *before* judging the response; otherwise it measures the response against the page just left. Related: `syncChallengeSearchUrl` must never delete `dl=` while a committed selection the current tier still backs is waiting on a refresh, or it discards the user's selection on the strength of the very response about to be re-run. Both caught in v0.13.0 QA as "returning to a filtered search drops the level and rewrites the URL".
- **Boot.dev can restore `d=` AFTER the navigation Catalyst adopted.** The nav-bar Training → Search link navigates with no query at all and only then writes its remembered difficulty into the URL from its Vue store. Adopting once per route change therefore saw no tier, restored nothing, and never looked again because the path had stopped changing. `ensureTrainingGroundsUiState` watches a `d=|dl=` key and re-adopts whenever it changes *without* a route change, then heals the rendered results. Note this is safe only because the remembered selection is rewritten on every commit — otherwise re-adopting could resurrect a cleared pick.
- **The selection must survive SPA navigation, because Boot.dev's own filters do.** Boot.dev keeps its difficulty in a Vue store, so leaving the search page and returning restores `d=` — but the URL it rebuilds carries no `dl=`, because it doesn't know that param exists. Adopting that URL therefore dropped Catalyst's selection on every return, and also wiped a selection that had just been committed when a search was started from the catalog page. `rememberedChallengeSelection` (module-level, tab-lifetime, never stored) holds the last committed selection and is restored **only when the route's `d=` still names its tier** — which is what keeps it from resurrecting a filter Boot.dev has dropped. A `dl=` present in the URL always wins; memory only fills a gap. Committing an empty selection overwrites the memory, so clearing the levels genuinely clears them.
- **Two corollaries of the same principle.** The gold dot is driven by what the last relayed search *actually* filtered (`lastChallengeSearch.filtered`), never by the committed selection — otherwise it advertises a filter that isn't in effect, which is what left it lit on the catalog page. And internal navigation (landing ↔ search) **re-adopts from the destination URL** rather than carrying the committed selection across, since the catalog page has no filter at all.
- **The native tier must be read while the popover is OPEN, and remembered.** The search normally runs after the popover has closed, where the tier can only come from `d=` in the URL — which does not exist yet on a first search and still names the *previous* tier right after a change. `commitChallengeSelection` therefore trusts the `pendingNativeTier` captured by the ensure tick and re-resolves only when the popover is still open. Re-resolving unconditionally intersected the selection against an empty tier and wiped it before `data-be-dl` was written, so the first search after picking a level silently didn't filter (caught in v0.13.0 QA).
- **An anchor rejected once can become available later — the mirror of "no API source exists" having a shelf life.** v0.13.0 recorded that the native difficulty pills carried no `aria-pressed`, which is why the tier had to be read from an image filename; by the 2026-08-15 capture they carried it. Nothing prompted a re-check — the note was simply believed for two releases. When a design is forced onto a worse anchor by an absence, write down what would make the better one usable, and look again when you are next in that markup.
- **Armor mechanics, because the Submit confirmation is built on them.** Boot.dev states them in-app (transcribed to `reference_data/catalyst_versions/v0.14.1_lesson_and_catalog_workflow/bootdev_sharpshooter_rules_2026-08-18.md`): the streak is protected if **the lesson has been completed**, **armor has already been used on the lesson**, or **you have armor** — and only the first two are *free*, since the third spends an armor to save the spree. That is why holding armor is not a reason to stay quiet, and why the armor count (absent from `/v1/users/lessons`) is not needed. Armor is a countable item from chests or the shop; the spree counts lesson completions only, never challenges, which is why the confirmation stays lessons-only. **A reset is not itself a protection**: measured 2026-08-18, a reset lesson with neither persistent protection broke an armor when failed 8 seconds later. The two free protections are exactly the fields that SURVIVE a reset — `successCount` and `armorUsedAt`; `previousSubmissionCode` does not. This **supersedes** the 2026-08-14 note that a reset lesson cannot cost armor.
- **"Nothing is at risk" is not the same question as "is it complete" (v0.14.1).** The Submit confirmation warns about losing armor, so the fields that answer it are the ones recording the penalty, not the one recording completion. `successCount` reads 3 on a *reset* lesson, so it means "ever completed", not "complete"; `isComplete`/`isReset` cannot see a failed lesson at all, which looks identical to an untouched one. When a feature's justification names a specific consequence, look for the field that records that consequence.
- **Do not derive a rule that protects something losable — measure it, and look for the platform's own statement (v0.14.1).** This one gate was revised three times on three coherent arguments, each sourced from real mechanics, and every one of them was wrong. `previousSubmissionCode` was dropped because failing with zero armor leaves `armorUsedAt` null (so surely the lesson could break an armor later — it cannot); then re-added because two failures in a row appeared to cost nothing the second time (they do — failing twice with no armor lost the spree both times); `hasCodeHistory` was floated to close an apparent gap, and is true in exactly the post-reset state where an armor *does* break. What ended it was Boot.dev's own in-app description of the rules plus one targeted test, not more reasoning. **Look for the platform's stated rules before deriving them**, and treat an apparent "harmless false positive" as suspect too — the gap here turned out to be the rule being right.
- **Graceful degradation is what makes a rename invisible (v0.12.2).** Every feature here is built to show less rather than break when a value is missing, so a renamed field produces a healthy-looking UI doing nothing. The counterweight is `warnOnce` / `reportUsableFields` (utils.js): cheap boundary checks that log once per session when a non-empty response yields **zero** usable values for a field a feature depends on. Wired into the all-time/daily/karma board handlers, `distillHeatmap`, `handleDashboardContent`, and the challenge-search relay. When adding a feature that reads a new API field, add the corresponding check — that, not more casing fallbacks, is the lesson of v0.12.1. **v0.13.1 added the other half:** `reportEndpointFailure` (utils.js), called from the non-2xx drop in `routeResponse`, warns once per session per path after **2 consecutive** failures. Counting is per *normalized* path (`/v1/users/public/{handle}`) so ten tracked handles hitting one broken endpoint aggregate into one signal; 401/403 never count (queued and retried elsewhere) and neither does a 404 on the public-user family, which is the normal answer for a mistyped handle. **More fallbacks make this worse:** a cross-semantic fallback (`XPEarned ?? XP` — trailing-24h XP falling back to a *lifetime* total) turns a missing value into a plausible wrong one, which is strictly harder to notice. Those were removed in v0.12.2.
- **A rename can move the CONTAINER, not just the fields (v0.14.2).** When Boot.dev migrated the leaderboard DTOs on 2026-08-19 the league boards' envelope key went with them — `LeagueMembers` -> `leagueMembers` — so `getLeaderboardEntries` matched nothing and returned `[]`. Both League comparison boards then failed the one way nothing catches: `reportUsableFields` only ever sees a **non-empty** list, so an empty one is indistinguishable from a quiet board, and those two handlers were the only leaderboard handlers with no check at all. Dual-casing the entry fields alone would have shipped looking complete and left them broken. Both the envelope table (`LEADERBOARD_ENVELOPE_KEYS`) and the field table (`API_FIELD_ALIASES`) are now explicit and both are pinned by `check_leaderboard_casing.mjs`. **When a response is wrapped, the wrapper is a field too.**
- **League formats were in a mixed rollout on 2026-08-19.** A new-format league was observed with 10 members on a 14-day cycle, while some users were still finishing the previous 25-member league format. **Nothing in Catalyst depends on either league size or cycle length** — it reads neither `leagueName`, `expiresAt` nor `memberLimit` off the league response, and the `ExpiresAt` handling in `boss.js` belongs to boss events, not leagues. The two league request URLs still use `?limit=25`, matching Boot.dev's current request shape even for the observed 10-member league; the server returned only the 10 available members. Keep 25 while both formats coexist rather than assuming the rollout is complete. Boot.dev may change that request limit after the rollout, but that has not been observed. **`memberLimit` is not the visible league size** — the 2026-08-19 envelope reported `memberLimit: 30` while the league held 10 members and the page said "10 of 10 league members". What it means is unresolved; do not use it as a member count without measuring first.
- **Casing aliases must be verified, not derived (v0.14.2).** `ProfileImageURL -> profileImageURL`, `XPForLevel -> xpForLevel`, `GithubCommits -> githubCommits`, `LeaderboardXPRankAlltime -> leaderboardXPRankAlltime` — every one keeps interior or trailing capitals, so a generic lowercasing transform guesses wrong on exactly the fields whose failure is most visible (blank avatars on every row). `API_FIELD_ALIASES` is an explicit table for that reason, and `check_leaderboard_casing.mjs` writes the measured spellings out a second time, independently, so the two have to agree.
- **Not every lowercase key is a casing alias.** `getPersonalRows` builds its rows with `handle` / `name` / `avatar`, and those rows are passed back through the same accessors that read API entries — so those three keys are **Catalyst's own shape**, not camelCase API names, and they must keep their precedence. `handle` also happens to match the real camelCase spelling, which is the only reason handles kept resolving through the v0.14.2 outage while names and avatars did not. Check who constructs an object before treating one of its keys as an API alias.

- Personal-board daily XP for other users has no exact API source (the daily board is rolling-24h). `leaderboard.js` keeps per-user total-XP snapshots (`record.xpSnapshots`, `[t, xp]` pairs, ≤60, pruned >24.5h) harvested from every response that reveals a total, and `computeDailyXpView` picks the best of: live board value → snapshot-window delta → heatmap estimate → "–". `ESTIMATED_XP_PER_LESSON` (115) is a placeholder awaiting calibration from the maintainer's base-XP spreadsheet — update that one constant when real data lands.
- Personal-board daily karma has **no API source at all** (no daily karma board, nothing to backdate from), so `computeDailyKarmaView` is measured-or-unavailable only: `record.karmaSnapshots` mirrors the XP snapshot store, observed gains display immediately, and a confident 0 needs a ≥30-min watched window (`SNAPSHOT_MIN_WINDOW_MS`). The viewer's own comparison baseline lives in `be_current_user_karma` (storage.local, invalidated on handle change), fed by an own-stats request on leaderboard visits, the top-25 karma board, and passively-observed own **stats** responses (the public profile response has no karma field — confirmed 2026-07-31 — so only `/stats` contributes). All of that requires a known handle, which is why the `findNuxtCurrentUserHandle` fallback matters: without it a fresh install that never opened `/leaderboard` had no baseline and every Daily Karma comparison read unavailable.
- Backup & restore (options page, `backup.js`): the export is versioned JSON (`catalystExport` marker + `BACKUP_FORMAT_VERSION`, independent of the extension version — bump it only on **structural** changes; new settings keys or data sections are not format changes). Sections: `settings` (raw stored object, NOT normalized — unset flags must keep tracking future defaults), `personalLeaderboard` (handles + per-handle xp/karma snapshot series only; profile/stats/heatmap are refetched, never exported), `currentUser` (handle + own karma series; import-guarded to the same handle), `bossState` (`eventId`/`eventHigh`/`eventHighAt`/`allTimeHigh`, plus the current event's `aura` observation history — an additive, backward-compatible field inside the existing section, so `BACKUP_FORMAT_VERSION` is unchanged; the event high and the aura history merge only for the same `eventId`, and the aura copy that observed MORE of the event wins whole rather than being summed — two devices watching the same hour would double-count it). Import is file-level strict (bad file → nothing written), entry-level lenient (bad handle/point skipped), and everything passes the same sanitizers on the way in. Hand-deleting a section from the JSON skips that section — documented user behavior, keep it working.
